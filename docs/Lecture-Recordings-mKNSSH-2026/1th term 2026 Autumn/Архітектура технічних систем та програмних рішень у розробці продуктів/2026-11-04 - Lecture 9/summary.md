# Лекція 9: Практичний воркшоп з архітектурних рішень

## TL;DR
Студенти розібрали п'ять із десяти запланованих кейсів і запропонували архітектурні рішення для кожного:
- **MVP малою командою:** моноліт замість мікросервісів і, можливо, PWA замість нативного застосунку.
- **Пікові навантаження й ліміти провайдера:** асинхронна обробка через чергу зі збереженням замовлення в БД.
- **Великі файли:** пряме завантаження в object storage через pre-signed URL.
- **Каскадні збої:** синхронний лише критичний крок, решта через події.
- **Застаріла SOAP-система:** anti-corruption layer.

Наприкінці лектор показав заповнений Architecture Vision Template, де застосовано багато з цих рішень.

## Key concepts
**Моноліт для MVP.** За малої команди й короткого терміну моноліт дає змогу швидше випустити продукт, ніж 6 мікросервісів на Kubernetes. Операційна складність мікросервісів не виправдана, якщо немає конкретної потреби в них.

**Progressive Web Application (PWA).** Вебзастосунок можна додати на домашній екран і запускати в окремому вікні, схожому на застосунок. Це дає головну перевагу застосунку — швидкий доступ без пошуку в браузері. Водночас потрібен лише один frontend і не треба проходити публікацію в магазинах застосунків.

**Вебверсія для пошуку клієнтів.** Без сайту сервіс складніше знайти через пошукові системи, а отже, складніше просувати. Для застосунку все одно може знадобитися хоча б landing page.

**Обмеження ШІ в тестуванні.** ШІ може реалізувати вимоги й тести, але рідко оцінює, чи зручно продуктом користуватися. Лектор порівняв це з «італійським страйком», коли працівники виконують лише те, що прямо прописано в інструкціях. Тому потрібен хоча б людський smoke test і цикл зворотного зв'язку.

**Асинхронна обробка через чергу.** Черга накопичує запити під час піку й передає їх провайдеру зі швидкістю, яку той витримує. Вона згладжує навантаження, але не має бути єдиним місцем зберігання даних, бо може впасти або втратити повідомлення.

**Redis і черга повідомлень.** Лектор наголосив, що Redis передусім є кешем типу key-value в оперативній пам'яті, а черга має інше призначення. Студенти заперечили, що Redis Streams можна використати для подій, а Celery може працювати з Redis як брокером. Лектор допустив такий варіант, якщо Streams дають потрібні гарантії, але вважає звичайну чергу логічнішою, якщо Redis ще не розгорнуто.

**Кеш із пакетним записом у БД.** Операції спочатку записуються в кеш, а потім пакетами передаються в базу, що зменшує навантаження на неї. Такий підхід має сенс, якщо вузьким місцем справді є БД. Якщо кеш упаде до відправлення пакета, зміни можна втратити, тому підтверджувати замовлення користувачу слід лише після запису в базу.

**Pre-signed URL.** Backend видає авторизованому клієнту посилання з короткоживучим токеном для прямого завантаження файлу в bucket. Великий трафік оминає API-сервер і не займає його робочі процеси. Сервер зберігає лише метадані про файл і власника.

**Circuit Breaker.** Цей патерн запропонувала студентка, щоб збій одного сервісу не блокував решту процесу. Наприклад, недоступність сервісу бонусів не повинна заважати оформити замовлення.

**Transactional Outbox.** Студентка запропонувала записувати операції в БД, а окремий процес періодично шукатиме необроблені записи. Так сервіс після відновлення зможе завершити відкладену роботу, а користувач тим часом уже матиме оформлене замовлення.

**Синхронні та асинхронні кроки.** Синхронним варто залишати лише те, без чого бізнес-операція неможлива. У кейсі доставки це підтвердження від ресторану, а бонуси, push-сповіщення й аналітику можна обробляти через події за принципом fire and forget.

**Різна цінність подій із часом.** Після відновлення системи не всі події варто обробляти однаково. Бонуси й аналітику потрібно опрацювати навіть із запізненням, а застаріле push-сповіщення про прийняте замовлення лише дратуватиме клієнта.

**Anti-corruption layer (ACL).** Це проміжний сервіс-адаптер між новим клієнтом і застарілою системою, який перетворює її формат на зручний для клієнта. Він ізолює застосунок від особливостей legacy-інтерфейсу і є тимчасовим рішенням до заміни core-системи. Оновити ACL значно простіше, ніж щоразу публікувати нову версію мобільного застосунку.

**Decision log.** Це журнал архітектурних рішень у документі Architecture Vision. Він пов'язує рішення з конкретними драйверами, застосованими патернами й тактиками та trade-offs.

## Formulas, code and examples
### Кейс 1: сервіс виклику майстрів
**Умови:** 4 розробники, MVP за 4 місяці, модулі замовлень, майстрів та оплати. Початкова пропозиція — 6 мікросервісів на Kubernetes.

**Рішення, яке обговорили:**
- Монолітний сервер зі спільним backend для всіх клієнтів.
- Реляційна БД, наприклад PostgreSQL, бо замовлення мають переважно однакові поля.
- Для клієнта є два варіанти: React і React Native або один frontend як PWA, зокрема на Python-фреймворку.
- Flet студент назвав можливим варіантом для кросплатформного застосунку на Python.

**Ризик публікації:** за словами лектора, перша публікація в App Store може тривати довго, а Google Play вимагає відгуків від 10 незалежних тестувальників. Тому застосунок доведеться завершити приблизно за 2,5 місяця, а не за 4.

### Кейс 2: Чорна п'ятниця
**Умови:** зазвичай 2 замовлення/с, у пік близько 50 замовлень/с, API синхронний. Провайдер приймає до 20 запитів/с і відхиляє решту. Точні параметри піка в транскрипті нерозбірливі.

**Запропонований потік:**
1. Записати замовлення в БД.
2. Поставити його в чергу.
3. Одразу повідомити користувача, що замовлення прийнято в обробку.
4. Проміжний сервіс читає чергу й надсилає провайдеру запити в межах ліміту.
5. Сервіс записує результат платежу в БД.
6. Cron job періодично шукає завислі транзакції й повертає їх у чергу.

### Кейс 3: медична лабораторія
**Умови:** файли 5–25 МБ, близько 600 файлів за 30 хвилин, завантаження через API-сервер на EC2 триває 1–2 хвилини. Через зайняті робочі процеси інші користувачі отримують тайм-аути.

**Рішення:**
1. Авторизований frontend запитує в backend посилання для завантаження.
2. Backend фіксує користувача й тип документа, а потім видає pre-signed URL.
3. Frontend завантажує файл напряму в S3.
4. Frontend повідомляє backend про завершення.
5. Коли лікар відкриває документ, backend створює окреме посилання для перегляду.

**Відхилені або слабші варіанти:**
- Масштабування з load balancer лише на час піка не прибирає великий трафік з API-сервера.
- Публічний bucket неприйнятний, бо туди можна завантажити що завгодно, а медичні дані потребують захисту.
- Довший тайм-аут технічно можливий на всіх проміжних вузлах, але лектор вважає довге відкрите з'єднання поганим рішенням.

### Кейс 4: доставка їжі
**Умови:** послідовний pipeline охоплює виклик ресторану, бонуси, push-сповіщення й аналітику. Падіння сервісу бонусів не дає клієнтам оформити замовлення, а маркетинг постійно просить додавати нові кроки.

| Крок | Комунікація | Поведінка після збою |
|---|---|---|
| Виклик ресторану | Синхронна | Без підтвердження замовлення не продовжується |
| Бонуси | Події | Обробити пізніше |
| Push-сповіщення | Події | Застарілі сповіщення не надсилати |
| Аналітика | Події | Обробити пізніше |

Щоб не втратити важливі події під час збою черги, їх можна зберігати в БД або застосувати event sourcing.

### Кейс 5: страхова компанія
**Умови:** нова мобільна апка працює з core-системою віком близько 20 років через SOAP/XML. Поля мають дивні назви, дані оновлюються лише вночі, формати змінюються, а заміна системи запланована аж через 3 роки.

**Рішення:** `Мобільна апка → Anti-corruption layer → Core-система (SOAP/XML)`

**Що врахувати:**
- **Затримка:** з'являється додатковий мережевий вузол, хоча для страхового сервісу це не має бути суттєвою проблемою.
- **Коректність:** перетворення форматів потрібно перевіряти й підтримувати.
- **Масштабування:** ACL не повинен ставати вузьким місцем і має вміти балансувати запити між екземплярами core-системи, якщо вона масштабується горизонтально.

**Твердження лектора про SOAP:** SOAP він назвав stateful, а REST — stateless. Він також зазначив, що REST не вимагає саме JSON.

### Приклад Architecture Vision: оренда автомобілів
- **Документ:** контекстна діаграма, діаграма контейнерів, таблиці елементів, decision log і таблиця статусу драйверів.
- **Клієнти:** застосунок для орендарів, окремий застосунок для технічного персоналу, вебінтерфейс для підтримки.
- **Вхід:** gateway із rate limiting і балансуванням навантаження.
- **Backend:** один моноліт.
- **Дані:** PostgreSQL для основних даних і object storage в ЄС для фото пошкоджень та документів. Розміщення в ЄС пов'язане з вимогами GDPR.
- **Завантаження файлів:** напряму в S3 через pre-signed URL.
- **Зовнішні сервіси:** запит записується в БД, окремий сервіс ставить його в чергу, надсилає та записує результат. Невдалий запит можна повторити, а користувач бачить статус перевірки або отримує push-сповіщення.
- **Статус драйверів:** можна додати скриншот Kanban-дошки, де видно, що адресовано повністю, а що частково.

## Open questions
- Trade-offs детально розглянуть на наступній лекції.
- Лише п'ять із десяти запланованих кейсів встигли розібрати. Чи повернуться до решти, лектор не сказав.
- Лектор не перевіряв, чи дають Redis Streams усі гарантії черги, зокрема гарантовану доставку.
- Питання розподілених транзакцій і втрати пакета змін під час падіння кеша лише позначили, але не розв'язали.
- Лектор забув увімкнути запис. Він попросив Максима поширити власний запис, якщо той є, і пообіцяв поширити заповнений шаблон.

## Glossary
- **MVP:** мінімальна версія продукту, достатня для запуску й перевірки ідеї.
- **PWA (Progressive Web Application):** вебзастосунок, який можна встановити на пристрій і запускати подібно до звичайного застосунку.
- **React Native:** фреймворк для створення мобільних застосунків на основі React, окремих від вебверсії.
- **Flet:** названий студентом Python-фреймворк для кросплатформних застосунків.
- **Smoke test:** базова перевірка основних функцій продукту.
- **Message queue:** компонент, який зберігає повідомлення для подальшої обробки споживачами.
- **Redis:** сховище key-value в оперативній пам'яті, яке в лекції розглядали насамперед як кеш.
- **Redis Streams:** структура даних у Redis для роботи з потоками подій.
- **Celery:** обробник фонових задач, що працює через брокер повідомлень.
- **Read-through cache:** кеш, який у разі відсутності даних читає їх із БД.
- **Write-through cache:** кеш, через який записи проходять до БД.
- **Шардинг:** розподіл даних бази між кількома вузлами.
- **Cron job:** задача, що запускається за розкладом.
- **Object storage:** сховище для файлів та інших неструктурованих об'єктів.
- **Bucket:** контейнер для об'єктів в object storage.
- **Pre-signed URL:** тимчасове підписане посилання для доступу до об'єкта без проходження файлу через API-сервер.
- **Circuit Breaker:** патерн, що обмежує поширення збою залежного сервісу на решту системи.
- **Transactional Outbox:** патерн, за якого операції для подальшої обробки спочатку зберігаються в БД.
- **Fire and forget:** надсилання події без очікування відповіді обробника.
- **Event sourcing:** підхід, за якого зміни стану зберігаються як послідовність подій.
- **SOAP:** протокол обміну повідомленнями на основі XML, характерний для старої системи з кейсу.
- **REST:** архітектурний стиль API без зберігання стану клієнта на сервері між запитами.
- **Anti-corruption layer:** адаптер, що ізолює нову систему від моделі та формату даних старої.
- **Bottleneck:** компонент, який обмежує продуктивність усієї системи.
- **GDPR:** законодавство ЄС про захист персональних даних.
- **Architecture Vision Template:** шаблон документа з описом архітектурного бачення, діаграмами й рішеннями.
- **Decision log:** журнал архітектурних рішень та їх обґрунтувань.
- **Trade-off:** компроміс, за якого перевага одного рішення супроводжується певною втратою чи обмеженням.
